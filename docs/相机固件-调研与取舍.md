## 二、`nikon-fw-key-tool`：能力与支持矩阵

一句话：把尼康固件镜像拆开（恢复 XOR 表 → 解密），改完再打回去（重算 CRC 与头部摘要）。

- **密钥恢复 + 解密**：Z5 / Z6 / Z6II / Z7 / Z7II / Z8 / Z9 / Z30 / Z50 / Zfc。
- **签名密钥恢复 + 重打包**：**只有 Z8 / Z9**。
- README 原话：`Z f、Z 5II、Z 50II、Z 6III and ZR use a newer scheme that this tool does not support`
  → **Z5II 明确不在支持范围**（新方案）。
- 它文档化的固件外层格式（z8/z9 那一代）：
  - 32 字节明文头（20 字节 SHA1 摘要 + 12 个未识别字节）+ body；
  - body `0x00` 处是 **32 个 ASCII 空格**的 label，`0x20` 处 BE32 表示模块数/目录大小；
    目录项 16 字节名；模块前缀 `ex`(ExMCU) / `_tpj01` / `eg`(主应用 Engine) / `vr`(IBIS) / `li`(第二核 Linux)；
  - 机型号 `2070` = Z8、`1990` = Z9、`1985` = Zfc；
  - XOR 三张 256 字节表，周期 2²⁴ = 16 MiB；CRC16 多项式 `0x1021`、初值 0、无反射；
  - 头部摘要 `header[0:20] == SHA1(decrypted_body || K8)`（`K8` 为机型相关 8 字节密钥）；
  - 退出码 0–11；仓库不含任何固件/密钥，需自备镜像。
- 它**不提供固件**，也不含字体/图标/校准数据。

## 三、我们手里那份 Z5II 固件：`Z5_2_0120.bin`

| 项 | 值 |
|---|---|
| 位置 | 工作区根目录 `E:\BaiduNetdiskDownload\dsh\video-to-camera-mov\Z5_2_0120.bin` |
| 大小 | **108,716,229 B（103.7 MB）** |
| SHA256 | `96FA8C2D735864C4C612DEE498818F2E3B6911458B13AD55BEFCFE9FFDF35AF9` |
| 文件时间 | 2026-10-10 21:07 |
| 版本号 | 文件名按尼康惯例 = Z5II 固件 **C1.20** |
| 版本库 | **不进版本库**：`.gitignore` 已有 `/*.bin`（相机固件属大二进制，且不宜公开） |

**只读探测结果（2026-10-17，未修改文件、未解密、未联网）**：

- 前 32 字节：`42 06 01 F5 7F 69 30 8E AB 4D 2A 4E A3 F4 86 E2 56 D9 3C 6D 8F 16 5C 96 8E 99 E4 D2 0A 02 9F B3`
- `0x20` 处 32 字节**不是** 32 个 ASCII 空格（而是高熵数据：`56 45 E6 2D 69 EE 42 BD …`）
- `0x40` 处 BE32 = 3,403,806,820（不像模块数）；其后按 16 字节切分也全是高熵

→ **结论：这份 Z5II 固件的**外层**就不是 nikon-fw-key-tool 文档化的那套格式**，
连模块目录都读不出来，与我们已知的「Z5II 用新方案、该工具不支持」一致。
拿它跑 nikon-fw-key-tool 不会有结果，**这条路不做**。

## 四、真正从这些仓库拿到的、已经落地的部分

借鉴的是**方法**，不是固件：

| 落地物 | 内容 |
|---|---|
| `tools/nikon-box-audit.py` | 20 项盒级审查：顶层盒链、`moov ≤ 16 MiB`、轨道结构、`stco/co64` 恰好一个、`stsc` 严格子集（首项 chunk=1、spc≠0、sdi=1）、chunk 映射单调、样本越界、无重排（`ctts`）、mdat 数据区被样本铺满、逐包与 ffprobe 对照 |
| `tools/box-mutant.py` | 12 种 mutant 阴性对照（截断/平移/stsz 越界…）；**每加一条检查，都要有能把它打红的 mutant** |
| `tools/verify-output.py --extra` | 43 项门禁 + 20 项附加审查一次跑完，附加结论也吐 `##CAMMOV` JSON |
| `docs/尼康ISO-BMFF子集-参考.md` | 子集清单、证据门禁、阴阳对照矩阵、局限 |

**「结论必须可独立复核」这条纪律**就是从 `z9-qemu/tools/recording_files.py` 学来的：
给出结论前必须同时满足「文件逐字节未变」「没有越界写」「每个字段都与独立来源对照过」。
我们把它写成了阴阳对照矩阵（12 个坏文件必须被打红、13 个好文件必须全绿）。

## 五、没采用的两条路（以及为什么留着）

1. **刷固件/改相机**（`WonderLantern-z6` 那条路：卡根放 `cn/EG162080.BIN` + 核心文件走
   Setup→固件版本 刷入，能加长曝光、倒计时、自定义快门声）
   → **与项目承诺相反**（我们卖的就是「不改相机、只放文件」），法务与保修风险都高，**不采用**。
2. **跑 QEMU 模拟器拿「固件自己写的 MOV」**（`z9-qemu`/`zr-qemu` 里已在模拟器里跑通固件
   自己的录制流水线，产物是相机命名的 `DCIM/100NIKON/DSC_0001.MOV`，909 帧 / 30.330300 s）
   → 这是公开渠道**唯一**能拿到「尼康自己写的容器」当基准的办法。代价：自备 Z9/ZR 固件 +
   Linux/WSL（`ubuntu-noble-nikon`）+ 构建 QEMU 与固件加载；且他们自标
   `Movie recording incomplete` / `native_movie_accepted: false` / 不含物理相机验证；
   法务灰区，**只能当研究，不能进产品**。→ **留作将来选项**，需要时再评估。

## 六、边界（已定，不要再漂移）

- 本项目**不改相机、不刷固件、不发布任何固件或其派生数据**；公开仓库继续只有转换器。
- `Z5_2_0120.bin` 只作为本机只读研究对象，不进版本库、不进安装包、不上传。
- 相机行为的结论，**优先用真机实验 + 自研门禁**得到；固件逆向只在真机路线卡死时才作为备选。

## 七、与我们已解问题的关系

已经靠真机 + 自研门禁解掉的（**不依赖固件逆向**）：

| 结论 | 手段 |
|---|---|
| `tkhd.duration` 必须保留模板值（相机拿它夹快进） | 真机反例（改「正确值」→ 卡死） |
| 分块必须每 0.5 秒且**整齐**（>512 s 的浮点漂移 → 快进不夹紧） | 门禁收紧 + 复算脚本 `tools/chunk-drift-demo.py`（见《工作记录-2026-10-07-彻夜之歌6部转卡.md》§十三） |
| `mdat` 偏移必须落在 128 KiB 的整数倍（抬高时平移 `co64`） | 相机原片 9 个样本统计 + 真机验证 |
| 缩略图必须是相机风格 JPEG（NCDT 三张：160×120 / 640×360 / 全分辨率） | 真机验证 |
| 帧率 / PTL tier / level 与相机原片对齐 | trace-diff 逐字段对照 |

**仍然只有相机内部代码能回答的**：相机建索引、判定「可跳转范围」的具体逻辑。
不过 2026-10-17 找到的**分块漂移**已经用实证解释了「长片能播、快进不夹紧」的主因，
所以 QEMU 这条重路目前**不必走**。

## 八、下一步（按代价从低到高）

1. **零成本**：继续观察 `nikon-fw-key-tool` 是否补上 Z5II/Zf/Z6III 的「新方案」支持
   （若支持，才有条件谈「解我们这份 `Z5_2_0120.bin`」）。
2. **零成本**：把从他们那里学到的检查思路继续用在自研门禁上（新发现的相机特性都要配 mutant）。
3. **高成本（暂不做）**：WSL + `z9-qemu` + 自备 Z9 固件，拿固件自己写的 MOV 当基准，
   对照「相机判定快进范围」的真实输入。
