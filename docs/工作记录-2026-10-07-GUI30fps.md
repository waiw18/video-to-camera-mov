## 2. 图形界面改了什么（`app/main.py`）

- **输出帧率可选**：普通模式与高级模式各一行下拉
  - `59.94 · 相机原生`（默认，等价于不传 `--fps`）
  - `跟随源 · 30fps/29.97 源保持原速（快一倍、体积减半）` → 只有源确实是
    29.5–30.5 fps 才真正生效，否则退回 59.94 并在界面上黄字说明（`fps_eff()`）
- **随包两个模板**：`BUNDLED_TPLS = {"": "DSC_8955.MOV", "source": "DSC_8960.MOV"}`，
  选「跟随源」时自动把模板换成 29.97 那个（只动随包模板，用户自选模板不碰）
- **码率预设三档**：`推荐 15 Mbps / fast`、`小体积 5 Mbps / fast（真机验证可播）`、
  `高画质 40 Mbps / medium`；高级模式码率候选 `5M / 15M / 40M`
- **并行段数走自动**：`run_convert()` 固定追加 `--jobs 0`（GOP 对齐 v2）；
  高级模式那一行从「1 · 单进程（已锁定）」改成「自动 · GOP 对齐 v2（真机验证）」
- 状态栏右下角改成 `门禁未运行 · 输出 59.94 · 模板 DSC_8955.MOV · v0.1.0-beta.1`
- 冒烟测试新增 `--fps-mode 59.94|source`，报告里打印「输出帧率 / 模板 / 码率 / 预设」

### 顺手修掉一个真 bug：`probe_info()` 读不到视频帧率

原来用 `ffprobe -of default=nw=1` 的平铺输出，每个流都打一遍同样的键，
**音频流会把 `r_frame_rate` 覆盖成 `0/0`**（`codec_type` 也被覆盖成 `audio`）。
后果：源信息行永远没有帧率，「跟随源」永远判不出 30fps —— 第一次 E2E 就撞上了：
报告明明写着 `--fps-mode source`，实际却按 59.94 编码（输出 390 帧 / `60000/1001`）、
模板也停在 DSC_8955。改成 `-print_format json -show_format -show_streams`，
取第一个 video 流的 `width/height/r_frame_rate`，音频则记成 `has_audio`。

## 3. 并行线程池：为什么默认改回 `cpu//jobs`

`--pools`（每段 x265 的线程池）曾一度改成「整机线程数」，短窗口测出来很快，
但那是**假快**——本配方 `wpp=0`，x265 只能靠帧级并行吃线程，
线程给多了 ABR 就欠码。同一段 90 秒窗口（720p30 源、2,697 帧、目标 15 Mbps）的
裸 ES 大小：

| 配置 | ES 大小 | 实际码率 |
|---|---|---|
| j6 + pools2（旧自动值） | 159.1 MB | 14.1 Mbps |
| j4 + pools3 | 157.0 MB | 13.9 Mbps |
| j4 + pools12 | 133.4 MB | 11.8 Mbps |
| j6 + pools8 | 127.8 MB | 11.3 Mbps |
| j6 + pools12 | 122.0 MB | 10.8 Mbps |
| j6 + pools24 | 125.6 MB | 11.1 Mbps |
| j12 + pools12 | 112.9 MB | 10.0 Mbps |

全长（同一源 254.86 s / 7,635 帧 / 15 Mbps）：

| 产物 | 并行 | 编码 | 整链 | ES 大小 | 实际码率 |
|---|---|---|---|---|---|
| `DSC_8963` | 6 段 × 2 线程 | 655.9 s | 696.0 s | 460,621,063 B | 14.5 Mbps |
| `DSC_8964` | 6 段 × 12 线程 | 696.0 s | 732.7 s | 385,564,009 B | 12.1 Mbps |

**pools=12 又慢又欠码**（少 16% 数据、还多花 40 秒），所以默认回到
`max(2, cpu // jobs)`；`--pools` 仍然保留，供「源本身很糊、只想要速度」时手动加。
顺带一个观察：pools 只改调度，产物照样 43/43（59.94 的 j4p8 对照件门禁通过）。

## 6. 踩坑与教训

1. **没留证据的结论就等于没有结论**：「8 Mbps 相机不认」查了一轮，发现当年既没存
   产物也没留日志（连卡上都没有那批文件），只能作废。以后测失败要留文件 + 日志。
2. **短窗口基准不可信**：90 秒窗口的 ES 大小受启动/尾部影响大，看耗时更会被
   「少编了数据」骗到；判断欠码要看 **ES 字节数**，判断速度要看同一目标码率下的耗时。
3. **并行不是免费的**：x265 在这个配方下 `wpp=0`，`--pools` 一味加大 = 欠码。
4. **冒烟必须断言关键项**：第一次 E2E 之所以能发现 `probe_info` 的坑，
   是因为它在报告里写了「输出帧率」这一行 —— 报告要写**能反驳自己的字段**。
5. **`ffprobe -of default=nw=1` 的多流键冲突**是经典坑：要么 `-select_streams v:0`，
   要么用 JSON。

## 8. 怎么把改动推到 GitHub（⚠️ 工作区 README ≠ 仓库 README）

- 工作区 `E:\BaiduNetdiskDownload\dsh\video-to-camera-mov\` **自己没有 remote**：
  公开仓库是从它里面**挑文件**发出去的（工作区 213 个 tracked 文件里有大量内部资料，
  公开的只有 57 个）。**别把工作区整个推上去。**
- 同名文件内容可能完全不同：`README.md` 工作区版是内部说明（4.7 KB / 91 行），
  仓库版是 **234 行的公开 README**（11.6 KB，带下载链接、硬约束表、工具清单）。
  推送时**只能给仓库版打补丁**，整文件覆盖会把这 234 行削成 91 行。
- 实操流程（2026-10-07 验证通过，commit `4b15b16`）：

```powershell
$tmp = Join-Path $env:TEMP "ghpush"
git clone git@github.com:waiw18/video-to-camera-mov.git $tmp   # HTTPS 会撞 schannel，用 SSH
# 把要更新的文件从工作区拷进 $tmp，行尾统一转成 LF（否则整文件 CRLF 噪音）
#   tools/video-to-camera-mov.py / app/main.py / docs/*.md …
#   README.md 用 python 做精确替换（每处断言只命中 1 次），不要整文件覆盖
git -C $tmp add -A
git -C $tmp commit -F commit_msg.txt
git -C $tmp push origin HEAD:main
```

- 判断「哪些文件真的变了」不要靠 `Get-FileHash` 一把梭：先用
  `git ls-files -z` 列出仓库文件，再用 Python 逐文件比对并把 CRLF 归一 ——
  否则 43 个「只差换行」的文件会把真正的 6 处差异淹掉。
