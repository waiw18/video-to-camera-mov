# 码流字段对齐：相机 vs 本工具（实测）

基准：相机 `DSC_8955.MOV`（1080p60 H.265 / PCM）
比对：ffmpeg 的 `trace_headers` 位流过滤器，逐语法元素解析后对比
工具：`python tools/trace-diff.py`（需先落盘两份 trace）

结论先行：**相机对码流的要求非常具体**。NVENC 和 x265 的默认配置都与相机有实质差异，
必须显式对齐。已定位的差异按严重程度排列如下。

---

## 一、致命级（会导致"能识别但读取无限加载"）

### 1.1 WPP / entry point offsets ★最可疑

| 字段 | 相机 | x265 默认 |
|---|---|---|
| `entropy_coding_sync_enabled_flag`（PPS）| **0** | 1 |
| 切片头 `num_entry_point_offsets` | **无** | **16 个** |

x265 默认开启 WPP（波前并行），于是**每个切片头都塞进十几个 entry point 偏移**。
相机的硬件解码器既不开 WPP 也不认 entry point，一路卡在加载。

**修法**：x265 加 `wpp=0`。修好后 `num_entry_point_offsets` 消失。

### 1.2 AUD 的 `pic_type` 写错

| 样本 | 相机 | 本工具（错） | 本工具（修好）|
|---|---|---|---|
| IDR | `46 01 10` | `46 01 08` | `46 01 10` |
| P 帧 | `46 01 30` | `46 01 18` | `46 01 30` |

AUD 载荷按 HEVC 规范是 `aud_pic_type u(3)` + 对齐位 1 + 4 个 0，即
**I → 0x10、P → 0x30、B → 0x50**。

原代码写的是 `(pic_type << 4) | 0x08`：
- 对齐位放到了 bit3（应为 bit4）
- **P 帧被标成 `000`，即"这是 I 帧"**

播放器用 AUD 判断图像类型，标错就会解码错乱/卡住。

### 1.3 `hvcC` 记录头 `profile_idc` 非法

原代码写 `0x20` = tier(High) + **profile_idc 0（未指定）**。
相机是 `0x21` = Main。现已改成逐字节对齐相机。

## 二、结构性差异（编码工具级）

| 字段 | 相机 | NVENC 默认 | 修法 |
|---|---|---|---|
| `log2_diff_max_min_luma_coding_block_size` | **3（CTU 64）** | 1（CTU 32）| 换 x265，默认 CTU 64 |
| `log2_min_luma_coding_block_size_minus3` | **0（8×8）** | 1（16×16）| x265 `min-cu-size=8` |
| `max_transform_hierarchy_depth_inter/intra` | **0** | 3 | x265 默认即为 0 |
| `scaling_list_enabled_flag` | **1** | 0 | x265 `scaling-list=default` |
| `sample_adaptive_offset_enabled_flag` | **0** | 1 | x265 `sao=0` |
| `sign_data_hiding_enabled_flag` | **0** | 1 | x265 `signhide=0` |
| `weighted_pred_flag` | **0** | 1 | x265 `weightp=0` |
| `five_minus_max_num_merge_cand` | **3** | 2 | x265 `max-merge=2` |
| `general_progressive_source_flag` 等 | **0** | 1 | 见下 |

**换 x265 是必须的**：NVENC 给不出 CTU 64。x265 配置对了之后
**13/15 个关键 SPS 字段与相机一致**。

## 三、文件自相矛盾（本工具自己引入的）

把 `hvcC` 记录头的 constraint flags 改成 0（对齐相机）后，
**码流内的 VPS/SPS 仍是 `0xF0`**（progressive + frame_only）。
同一个文件里两处声明不一致，相机很可能校验这一点。

**修法**：`zero_constraint_flags()` —— 在去转义后的 VPS/SPS 载荷里找
compat flags `60 00 00 00`，把它后面那个字节清零，再重新插入 emulation prevention。
（清零会多出一个 `00 00 03` 转义字节，长度 +1 属正常。）

## 四、视频尺寸：相机编的是 1088 而不是 1080 ★

很容易漏掉，但它是**真实的编码结构差异**：

| 字段 | 相机 `DSC_8955.MOV` | 本工具（原来）|
|---|---|---|
| `pic_width_in_luma_samples` | 1920 | 1920 |
| `pic_height_in_luma_samples` | **1088** | **1080** |
| `conformance_window_flag` | **1** | 0 |
| `conf_win_bottom_offset` | **4**（裁 4×2 = 8 行）| — |
| 容器 `tkhd` 尺寸 | 1920×1080 | 1920×1080 |

1080 不是 16 的倍数，硬件编码器习惯编 1088、再用 conformance window 裁掉 8 行。
本工具原先按 1080 直接编，**少了这个裁剪窗口**。

**补法**：源按 1920×1080 摆好后在底部补 8 行黑边 → 真编 1088 行 →
位级改写给 SPS 插入 `conformance_window_flag=1, bottom_offset=4` →
容器仍声明 1920×1080。
见 `tools/hevc-ps.py` 的 `sps_add_conformance_window()`、`tools/make-variants.py`。

## 五、位级改写参数集踩过的坑（都已修）

1. **`vps_reserved_0xffff_16bits`**：VPS 在 `vps_temporal_id_nesting_flag` 之后还有
   16 位保留字段，漏读会让后面全部错位。
2. **插入 vs 替换 `vps_timing_info_present_flag`**：必须**替换**原来那一位；
   插在它前面会留下多余的 0 位，parser 在 `vps_extension_flag` 之后本应直接读到
   `rbsp_stop_one_bit`，结果整个 VPS 解析失败（现象：VPS 之后的 SPS/PPS 全不被解析）。
3. **`profile_tier_level` 位顺序**：`general_level_idc` 在 constraint flags 之后、
   子层 present 标志之前，漏读会错位。
4. **Annex-B 尾部多余的 `00` 字节**（`trailing_zero_8bits`）：改写中间字段后按字节补零
   会让停止位位置错乱，必须先按"最后一个 1 位"规范化尾部。

## 六、仍然存在的差异（4 项）

| 字段 | 相机 | 本工具 | 能不能补 | 说明 |
|---|---|---|---|---|
| `lists_modification_present_flag` | 1 | 0 | **不能单独补** | 实测翻这一位会让切片头解析错位（12 帧 10 个 `alignment_bit_equal_to_one=0`）——它必须与切片头里的 `ref_pic_lists_modification()` 同时存在 |
| `sps_scaling_list_data_present_flag` | 1 | 0 | 需要 scaling list 文件 | x265 的 `scaling-list` 只有 `default`/`off` 合法（`intra`/`inter` 直接编码失败），`default` 给出 enabled=1 但 data_present=0 |
| `num_short_term_ref_pic_sets` | 2 | 0 | 需要重写切片头 | 相机把参考图像集放在 SPS 里；本工具是切片头内联 |
| `short_term_ref_pic_set_sps_flag` | 1 | 0 | 同上 | 与上一条联动 |

## 七、验证"外部文件是否被接受"（两步已通过）

`DSC_4450.MOV` = 相机 1080p 原片**逐字节复制、只改文件名** → **相机能播** ✅
→ 排除"相机只认自己录的文件"，容器布局、`NCDT`、`ftyp` 都没问题。

`DSC_4470.MOV` = 相机自己两段原片（`DSC_8955`+`DSC_8956`）拼成 10.2 秒，
码流 100% 相机原生，**容器由本工具重建** → **相机能播** ✅
→ **容器重建（多 chunk 的 stsc/co64/交错/时长）完全正确**，问题只可能在编码器输出。

## 九、当前配置（tools/video-to-camera-mov.py 的 x265 参数）

```
ref=1:bframes=0:keyint=30:min-keyint=30:aud=1:repeat-headers=1
ctu=64:min-cu-size=8:scaling-list=default:sao=0:level-idc=5.0
wpp=0:signhide=0:weightp=0:max-merge=2:open-gop=0
range=full:colorprim=bt709:transfer=bt709:colormatrix=bt709
```

**色彩必须用 x265 原生参数名**：ffmpeg 的 `-color_primaries/-color_trc` 经 libx265
包装后写成"未指定"(2)，相机是 bt709(1)，要用 `colorprim=bt709`。

注意：**不要**加 `tu-inter-depth=0` / `tu-intra-depth=0`（x265 要求 >=1，会编码失败）；
**不要**加 `-sar 0:0`（libx265 报 `Value nan for parameter 'sar' out of range`）。
