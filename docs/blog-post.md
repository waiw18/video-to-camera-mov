# 让普通视频在相机上播放的技术原理（以 Nikon Z5II 为例）

> **注意**
>
> - 目前还存在很大的性能问题：**i5-12450H 上，4 分钟的视频需要转换约 30 分钟**。
>   预计过几天优化好并发布程序。
> - 本项目是 **vibe coding** 的产物。
> - **本内容由 AI 编写。**
> - 文中所有数值均来自对相机原片的实测比对，结论为逆向推导所得，非厂商文档。

接下来是正文。

---

## 1. 问题与结论

把电脑上的普通视频拷进相机卡，症状有两种：

- 相机列表里**能识别**，播放时**一直加载**
- 直接提示**"无法显示此文件"**

**结论：相机不是在"兼容播放"，而是要求文件与它自己录制的文件同构。**
「解码无错误」只是必要条件，不是充分条件。

---

## 2. 三层判据

文件要在相机上播放，需同时满足三层：

**容器层** —— 盒子结构、媒体数据位置、样本表、交错顺序。
失败表现：能识别但一直加载。

**私有元数据层** —— 相机专有的资产描述块（含预览图）。
失败表现：缺失则提示"无法显示此文件"。

**码流层** —— HEVC 参数集与切片头。
失败表现：能识别但一直加载。

**诊断方法**

- 提示"无法显示此文件" → 问题在私有元数据层
- 能识别但一直加载 → 问题在容器层或码流层
- 区分后两者：把**相机原生码流**装入自建容器后试播。能播则容器层无问题

---

## 3. 容器层

### 3.1 媒体数据位置固定

1080p 文件的顶层布局为：

```
ftyp(24 字节) → moov → free → mdat@655360
```

4K 文件为 `mdat@1966080`。

原因是嵌入式读取器按固定偏移寻址，避免全文件扫描。`moov` 不足时用 `free` 盒精确补齐至 655360 字节。

### 3.2 样本表

- `stsd`：编码格式描述。视频为 `hvc1`，音频为 `lpcm`
- `stts`：样本时长。视频 `(N, 1001)` @60000；音频 `(N, 1)` @48000
- `stsc`：每 chunk 样本数。视频每 chunk **30** 个样本
- `stsz`：样本字节数。全等时使用紧凑格式
- `co64`：chunk 偏移，64 位
- `stss`：关键帧索引，每 30 帧一个

### 3.3 交错

音视频 chunk 需按时间交错，而非分段连续存放。

```
video chunk k = 第 30k .. 30k+29 个视频样本
audio chunk k = 覆盖至 video chunk k 结束时刻的全部音频样本
              起点 = floor(累计视频 tick / 60000 × 音频采样率)
              音频为 AAC 时再除以 1024
排列：v0, a0, v1, a1, …
```

音频 chunk 长度**不均匀**（实测 23、23、24、23、24 ……），由视频时间轴换算得出。

### 3.4 两个时基陷阱

- `elst.segment_duration` 使用**影片时基**（`mvhd.timescale`），非轨道时基
- `mvhd.duration` 必须 **不小于各轨时长**。实测源常见音频长于视频（254.862 秒 与 254.699 秒），
  若取视频时长会截断音频尾部

## 4. 私有元数据层（`moov/udta/NCDT`）

### 4.1 子盒

- `NCHD`：18 字节固定头，各文件相同
- `NCTG`：定长元数据记录表
- `NCTH`：JPEG 160×120
- `NCVW`：JPEG 全分辨率（1080p 约 484 KB）
- `NCM1`：JPEG 640×360
- `NCM2`：JPEG 1920×1080（1080p 文件中为空盒）
- `NCDB`：空盒

修改缩略图会改变子盒尺寸，**必须同步重建外层 `udta` 的 size 字段**，否则整棵 `moov` 解析错位。

### 4.2 无时长字段

对比三段时长不同的原片（228 / 384 / 144 帧），`NCHD` 逐字节相同，与内容相关的记录仅有：

- `0x13`：`[帧数, 0]`
- `0x16` / `0x17`：帧率
- `0x11` / `0x12`：拍摄时间（ASCII 本地时间）
- `0x19`：时区
- `0x101` / `0x102`：缩略图尺寸描述

**相机显示时长 = `0x13` 除以 `0x16`，实时计算。**

### 4.3 时间存两处

- 容器内（`mvhd` / `tkhd` / `mdhd`）：QuickTime 纪元秒，UTC，1904 年起算
- 私有元数据内（`NCTG 0x11` / `0x12`）：ASCII 本地时间

两者相差 `NCTG 0x19` 记录的时区偏移，须同时修改。

### 4.4 缩略图 JPEG 必须匹配相机格式

实测与 ffmpeg 默认输出的差别：

- Y 采样：相机 **2:1（4:2:2）**，ffmpeg 默认 2:2（4:2:0）
- 量化表：相机 **2 张**（DQT 段长 132），ffmpeg 默认 1 张（段长 67）
- 标记序列：相机为 `DQT DHT SOF0 SOS`，ffmpeg 默认多出 `APP0(JFIF)` 与 `COM`

**格式不符会导致整个文件被拒绝**，而非仅缩略图异常。

正确做法：使用 libjpeg 系编码器（如 Pillow，`subsampling=1` 输出即为 2:1 / 1:1 / 1:1），
沿用相机模板的量化表，将标记重排为相机顺序，去除 APP0 与 COM 段。

**注意**：不可用 ffmpeg 编码后仅修改 SOF 中的采样率字段。
ffmpeg 的 mjpeg 编码器即使输入 4:2:2，实际写出的采样率仍为其他值；
只改声明不改熵编码数据会导致 JPEG 损坏（实测每张 2 个解码错误）。

## 5. 码流层

### 5.1 参数集是语法依赖，不是声明

解码器解析编码单元时，需先由 SPS / PPS 确定：CTU 尺寸、最小编码块尺寸、
变换块递归深度、SAO 与 AMP 开关、CABAC 初始化标志位置、去块滤波参数位置、
参考帧列表是否修改等。

**这些字段被修改会导致切片数据解析错位**，因此只能在编码时决定，无法事后修补。

### 5.2 实测必须一致的字段

- `pic_height_in_luma_samples` = 1088
- `conformance_window_flag` = 1
- `conf_win_bottom_offset` = 4
- `log2_min_luma_coding_block_size_minus3` = 0（最小编码块 8×8）
- `log2_diff_max_min_luma_coding_block_size` = 3（CTU 64）
- `max_transform_hierarchy_depth_inter` = 0
- `max_transform_hierarchy_depth_intra` = 0
- `sample_adaptive_offset_enabled_flag` = 0
- `amp_enabled_flag` = 0
- `cabac_init_present_flag` = 0
- `deblocking_filter_control_present_flag` = 0
- `sign_data_hiding_enabled_flag` = 0
- `weighted_pred_flag` = 0
- `entropy_coding_sync_enabled_flag` = 0（WPP 关闭）
- `num_entry_point_offsets` = 不存在
- `five_minus_max_num_merge_cand` = 3
- `nal_hrd_parameters_present_flag` = 无
- `vps_timing_info_present_flag` = 1（1001 / 60000）
- `sps_max_dec_pic_buffering_minus1` = 1，`vps_max_dec_pic_buffering_minus1` = 1
- `sps_max_latency_increase_plus1` = 0，`vps_max_latency_increase_plus1` = 0
- `colour_primaries` = 1，`transfer_characteristics` = 1（BT.709）
- `video_full_range_flag` = 1
- `aspect_ratio_info_present_flag` = 0
- `general_frame_only_constraint_flag` = 0

### 5.3 编码高度为 1088

1080 不是 16 的倍数。硬件编码器将高度补至 16 的倍数（1088 = 68 × 16），
再以 `conformance_window` 裁除多余 8 行，最终显示 1080。

```
编码高度 = 显示高度向上取整到 16 的倍数
conf_win_bottom_offset = (编码高度 − 显示高度) / 2
```

按 1080 直接编码且无裁剪窗口时，相机表现为"能识别但一直加载"。

### 5.4 其它约束

- **关键帧类型**：相机全片仅 `IDR_W_RADL`，无 `CRA`。
  x265 默认开放 GOP 使用 CRA，须设 `open-gop=0`
- **WPP**：开启后切片头会附带多个 `entry_point_offset`，须设 `wpp=0`
- **AUD 载荷**：`pic_type(3 位) + 对齐位(1 位) + 0000`，I 帧为 `0x10`、P 帧为 `0x30`。
  对齐位在 bit 4
- **色彩**：须使用编码器原生参数名。经 ffmpeg 通用参数名包装后写入的是"未指定"
- **`hvcC` 自洽**：容器内参数集副本的记录头字段须与码流中的参数集一致
  （例如约束标志不得一处清零、一处保留原值）

## 6. 硬件编码器（NVENC）为何不可用

实测 NVENC 输出与相机相差 **16 个字段，其中 14 个无法修补**。

**编码块结构**

- CTU：相机 64，NVENC 32
- 最小编码块：相机 8×8，NVENC 16×16
- 变换块递归深度：相机 0，NVENC 3
- SAO：相机关，NVENC 开
- AMP：相机关，NVENC 开
- 量化表开关：相机开，NVENC 关

**PPS 开关**

- `cabac_init_present_flag`：相机 0，NVENC 1
- `deblocking_filter_control_present_flag`：相机 0，NVENC 1
- `num_ref_idx_active_override_flag`：相机 0，NVENC 1
- merge 候选数：相机 2，NVENC 5

**HRD**

- `nal_hrd_parameters_present_flag`：相机无，NVENC 有

**原因**：这些字段决定切片数据的解析方式。修改参数集声明而不修改数据，解码结果即为错误。
因此它们只能在编码时确定。

**结论**：相机实际要求使用与其自身编码器一致的配置。
可精确复现该配置的编码器为 x265（含上述参数约束）。
硬件编码器无法给出 CTU 64 + 最小编码块 8×8 + 关闭 SAO 的组合。

提速方式仅为更换 x265 预设：`medium` 换到 `fast` 约提速 2.6 倍，且关键参数实测保持一致。

## 7. 位级改写参数集的注意事项

x265 无对应开关的字段（VPS 时序信息、DPB、latency 等）需在 RBSP 位串上改写。

1. **防竞争字节**：解析前需 `unescape`，改写后需 `escape`
2. **`vps_reserved_0xffff_16bits`**：VPS 在 `vps_temporal_id_nesting_flag` 后有 16 位保留字段，
   漏读导致后续错位
3. **`profile_tier_level()` 位序**：`general_level_idc` 位于约束标志之后、子层标志之前
4. **插入与替换**：新增 VPS 时序信息须**替换**原 `vps_timing_info_present_flag` 位。
   若插在其前，残留的 `0` 会破坏尾部停止位结构，导致该参数集解析失败，
   且症状为**其后所有参数集均不被解析**，容易误判
5. **尾部多余零字节**：编码器输出在 NAL 尾部带 `trailing_zero_8bits`。
   改写中间字段后应按"最后一个 1 位"规范化尾部，再补齐至字节边界
6. **`st_ref_pic_set()`**：x265 通常为 0 个，部分编码器为 1 个，不跳过则解析中断
7. **不可单独修改的字段**：如 `lists_modification_present_flag` 属"允许"语义，
   须与切片头中对应语法同时存在。单独翻转会导致切片头解析错位

**验证要求**：位级改写后必须用独立解码器验证（`ffmpeg -v error` 输出为空）。
自写解析器会与自身错误一致，不构成验证。

## 8. 校验要点

- 顶层布局与 `mdat` 位置 —— 容器层判据
- `stbl` 子盒序列 —— 结构同构
- `mvhd` 不小于各轨时长，且等于最长轨 —— 防止音频尾部截断
- `NCDT` 存在且子盒同序 —— 缺失会提示"无法显示"
- `NCDT` 帧数等于实际帧数 —— 相机时长来源
- 容器 UTC 时间等于 `NCDT` 本地时间加时区 —— 两处时间一致性
- 缩略图标记序列、采样、量化表段数同相机，且**各自解码无错误** —— JPEG 格式影响整个文件
- 参数集与切片头字段 —— 码流层判据
- 整体解码无错误 —— 兜底

**参数集检查必须覆盖 P 帧切片头与 PPS 级开关。**
仅检查首帧（IDR）与少量 SPS / PPS 字段会遗漏大部分差异 —— 实测中一次失误即源于此：
漏检 16 处差异导致错误放行。

**同时不应过度收紧**：如 `num_negative_pics` 在可播放文件与相机之间本就不同（2 与 1），
属编码器实现差异，不应作为判据。
判据应仅来源于"已验证可播放的文件同样一致"的字段。

## 9. 已知局限

1. **必须重编码**，无法无损转封装。参数集须与相机一致，只能重新编码，存在画质损失与耗时
2. **无法使用硬件编码器**，只能软件编码
3. **依赖相机原片作为模板**（容器布局、私有元数据、缩略图量化表均取自模板）
4. **仅验证 1080p59.94**。4K 与其他帧率未实测；4K 文件中的第四张缩略图未重建
5. **长片仅验证至 4 分 15 秒 / 15267 帧**
6. **存在若干未对齐项**（显式量化表、SPS 内参考图像集、一个 PPS 开关）。
   经验证不影响播放，属已知差异而非已解决
7. **结论为逆向推导**，非官方文档。相机固件更新后可能失效
8. **私有元数据中部分非预览字段语义未明**，当前直接沿用模板值

## 10. 失败模式对照

- **"无法显示此文件"** —— 私有元数据缺失，或其外层盒 size 未重建
- **能识别、持续加载** —— 码流结构不符（CTU、SAO、关键帧类型、WPP、编码高度等）
- **仅播放开头数秒** —— `elst` 使用了轨道时基而非影片时基
- **音频尾部被截断** —— `mvhd` 时长小于音频轨时长
- **音画不同步** —— 音频 chunk 未按视频时间轴切分
- **显示时长错误** —— `0x13` 帧数未更新
- **缩略图为其他画面** —— 模板缩略图未替换
- **拍摄时间为其他视频** —— `NCTG 0x11` / `0x12` 与容器头未同时修改
- **文件被拒但解码无错误** —— 码流合法但编码器配置与相机不一致
