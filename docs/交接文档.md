## 1. 目标

让**电脑上的任意普通视频**能在 **Nikon Z5II** 上正常播放、时长正确、音视频同步、缩略图正确。

- 容器：**MOV**（MP4 不通，别浪费时间）
- 编码：**H.265/HEVC**，1920×1080，59.94 或 29.97 fps
- 音频：**PCM 24-bit 48 kHz 立体声**（`lpcm`，`sample_size=6`）
- 卡：`F:\DCIM\118NZ5_2\`，卷标 `NIKON Z5_2`，exFAT

**最终验收 = 在相机上真机能播、时长对、音视频同步、完整播完。**

### 2.0 ★★ 最终验证过的配方（2026-10-02 收口）

**`DSC_4558.MOV` 真机验证通过（能播 + 快进越界正常夹紧），且与基准 `DSC_4521.MOV`
逐字节只差 28 字节（全是拍摄时间戳）** —— 说明配方已完全固化：

```
59.94 fps（29.97 通道 2026-10-07 已打通并真机验证，见下）
全长（不要加 --duration）
--preset fast --bitrate 15M
--jobs 0（自动：长片 4 段 GOP 对齐并行 1.91×，短片自动单进程；求稳用 --jobs 1）
不要 --duration（真机未验证，见 §12）
```

**必须遵守的三条（都有真机反例）：**

| 项 | 要求 | 反例 |
|---|---|---|
| **`tkhd.duration`** | **保持模板原值（228,228 / 228,220），绝对不要改** | 改成"正确值"后快进越界不夹紧 → 卡死 |
| **PTL tier** | **59.94 → 0（Main）；29.97 → 1（跟随相机 29.97 原片，trace-diff 实测）** | 59.94 改成 1 → `DSC_4544` 相机直接无效 |
| **分块** | 每 **0.5 秒**一块（59.94 = 30 帧 / 音频 24,024）| 按"每 30 帧"算 → 29.97 全错 |
| **分块必须整齐** | 除末块外**每块的样本数都等于 0.5 秒**（音频 24,024）；分块表必须用**整数运算**算 | 浮点累加在 **512 秒**后开始 ±1 跳块 → `stsc` 几百条 → **长片快进不夹紧**（§见 `工作记录-2026-10-07-彻夜之歌6部转卡.md` §十三）|

**29.97 已打通并真机验证（2026-10-07）**：根因是 `keyint` 写死 30 —— 29.97 的
0.5 s 块是 **15 帧**，写死 30 → 一半的块不以 IDR 开头。现在 keyint/min-keyint 与分块
同源（59.94→30、29.97→15）：`DSC_9698.MOV` 全片（966 帧）转换 43/43 门禁全过；
trace-diff 对比 VPS/PPS 逐字段 0 差、SPS 仅剩 2 处与 59.94 同款的已知无害残差
（scaling list 系列与 SPS 内参考集，见《码流字段对齐-实测.md》）；full-tree 盒树逐项同值。
`--fps source` 基准：j1 129.2 s → **j6 65.4 s（1.98×，29.97 最优段数）**（详见 §8）。

**已知未解现象**：60 秒这类**短文件**快进越界时不夹紧（全长文件正常）。
只影响短文件，不影响全长交付版。

**长片快进不夹紧（2026-10-17 已找到根因并修好）**：不是"长短"本身，而是**音频分块的浮点漂移**——
旧的 `int(cum_v * fps_den / fps_num * 48000 + 1e-9)` 从**第 1022 块 = 512.0 秒**开始出现 ±1 个样本的
偏差（双精度 ULP 超过那个 1e-9），音频 `stsc` 从 1~2 条涨到几百条；相机原片一律是整齐的 24,024。
所以 8.5 分钟以内的产物一直正常（254 s 的 `DSC_4521` ✓、5 s 的 `DSC_9710` ✓），
20 分钟级的 `DSC_9701/9702` 则"能播、快进不夹紧"。写入端与检查端都已改成整数运算（提交 `9d4a337`），
门禁也把「分块 == 0.5 秒」收紧成「除末块外每块都相等」——修好后长片会被门禁**打红**（42/43），
旧产物需用 `output\rebuild-uniform.py` 重转。复算脚本：`tools/chunk-drift-demo.py`。

> ⚠ **这个修复在 `v0.1.0-beta.2` 之后才落地**（提交 `9d4a337`），beta.2 安装包里的转换器
> 仍会写出漂移分块（>8.5 分钟的文件），**下次发版必须带上**。

## 4. ★ 硬约束清单（相机要求，一条都不能少）

这些是**真机试出来的**，改任何一条相机就不认。`verify-output.py` 的 43 项就是围绕它们建的。

### 4.1 容器 / 缩略图

| 约束 | 值 | 不满足的后果 |
|---|---|---|
| 顶层布局 | `ftyp(24) moov free mdat@655360` | 相机不认 |
| `ftyp` 品牌 | `qt  ` + `niko`，minor=`0x00080​8c0` 一类的模板值 | 同上 |
| `udta/NCDT` | **必须有**，且子盒顺序 `NCHD NCTG NCTH NCVW NCM1 NCM2 NCDB` | 缺了报"无法显示此文件" |
| `NCDT 0x13` | `[帧数, 0]` | 时长显示错 |
| `NCDT 0x16/0x17` | 帧率 rational，**相机只认 `30000/1001` / `60000/1001`** | 认错帧率 → 快进 |
| 缩略图 | `NCTH` 160×120、`NCM1` 640×360、`NCVW` 全分辨率，**必须是"相机风格 JPEG"** | 换了普通 JPEG → **整个文件被拒** |

**"相机风格 JPEG" = 4:2:2（`Y=2:1, Cb=Cr=1:1`）+ 2 张量化表 + 标记只有 `DQT DHT SOF0 SOS`（无 APP0/COM）。**
用 `tools/camera-jpeg.py` 的 `pillow_camera_jpeg()`（Pillow + 相机量化表 + 标记重排）。

⚠️ **不能用 ffmpeg 编完再改 SOF 采样率**：ffmpeg 给 `yuvj422p` 时写的其实是
`2:2/1:2/1:2`，只改 SOF 声明不改熵数据 → JPEG 损坏（每张 2 个解码错误）→ 相机拒绝整个文件。

### 4.2 时间字段（★ 这两个坑最隐蔽）

```
mvhd.timescale        = 视频轨时基        （59.94 -> 60000；29.97 -> 30000）
视频 mdhd.timescale   = 同上
视频 stts             = (帧数, 1001)
音频 mdhd.timescale   = 48000，stts = (样本数, 1)
mvhd.duration         = 最长轨道的时长（影片时基）
tkhd.duration         = 该轨道自己的时长（影片时基）★ 两条轨道都要改
elst.segment_duration = 影片时基
```

- **`tkhd.duration` 漏改** → 相机显示的时长是模板那条片子的（实测漏了很久）。
- **视频时基不能写成 `30`**：数学上等价，但相机只认 `60000 / 30000` 那套，
  看到小值时**退回默认 1080p60 模式** → **快进 2× + 时长错 + 音视频不齐 + 播不全**。
  用 `normalize_fps()` 归一，并且**帧数要按归一后的帧率算**。

### 4.3 H.265 码流（跟相机逐字段对齐）

| 项 | 相机值 | 说明 |
|---|---|---|
| Profile / Tier / Level | Main / **high tier** / **4.1(123)**（1080p）；PTL constraint flags 全 0 | 相机 1080p60 是 123 |
| CTU / 最小编码块 | **64 / 8×8** | `log2_diff_max_min_luma_coding_block_size=3` |
| TU 递归深度 inter/intra | **0 / 0** | |
| SAO / AMP | **关 / 关** | |
| scaling list | 开（`scaling_list_enabled_flag=1`）| |
| **WPP** | **关**（`entropy_coding_sync_enabled_flag=0`）| 开了切片头会多 entry points |
| `sign_data_hiding` / `weighted_pred` | 0 / 0 | |
| 关键帧 | **全部 `IDR_W_RADL(19)`**，不能有 CRA(21) | 开放 GOP 用 CRA → 相机卡加载 |
| 参考帧 | `ref=1`、无 B 帧、`sps_max_num_reorder_pics=0` | |
| DPB / latency | `sps/vps_max_dec_pic_buffering_minus1=1`、`latency_plus1=0` | |
| VPS 时序 | `vps_timing_info_present_flag=1`，1001 与 output fps | |
| 尺寸 | `pic_width=1920`、**`pic_height=1088`** + **`conformance_window_flag=1, conf_win_bottom_offset=4`** | ★ 见下 |
| AUD | `46 01 10`（I）/ `46 01 30`（P），每样本一个 | |

### 4.4 ★ 最关键的一条：编 1088 行 + 裁剪窗口

1080 不是 16 的倍数，**相机自己就是编 1920×1088 再用 `conformance_window` 裁 8 行**显示 1080。
本工具早先按 1080 直接编、没有裁剪窗口 → 相机"能识别但读取无限加载"。

**这是整件事的根因。** 修法：编码时在底部补 8 行黑边（真编 1088），
再用 `hevc-ps.sps_add_conformance_window()` 给 SPS 插裁剪窗口，容器仍声明 1080。

### 4.5 ❌ 不要用 GPU（NVENC）

实测 NVENC 出的文件**相机不认**（`DSC_4511`、用户自测的 `DSC_4520` 都失败）。
不是容器问题，是码流本身差 **16 个字段、其中 14 个改不了**：

```
CTU 32(vs 64)、minCU 16(vs 8)、TU 深度 3(vs 0)、SAO 开、AMP 开、scaling list 关
cabac_init_present_flag=1、deblocking_filter_control_present_flag=1、
num_ref_idx_active_override_flag=1、merge 候选 5(vs 2)、整套 HRD 参数
```

这些一旦改就会让切片头错位。**相机等于在要求"它自己那套编码器配置"，只有 x265 能复现。**

### 4.6 ★ 分块规则：每 0.5 秒一块（不是每 30 帧）

**铁证来自相机自己的两个原片**（每块都恰好 0.5005 s）：

| 原片 | 视频每块 | 音频每块 |
|---|---|---|
| `DSC_8955.MOV`（59.94）| **30 帧** = 0.5005 s | **24,024 样本** |
| `DSC_8960.MOV`（29.97）| **15 帧** = 0.5005 s | **24,024 样本** |

**59.94 时 30 帧恰好也是 0.5 秒**，所以"每 30 帧"这个错误假设长期没暴露；
一到 29.97 就全错（视频块长一倍、音频块只覆盖一半或长一倍）→ 相机播到一半跳出 / 无法播放。

修法（`make-camera-mov.py`）：

```python
VPC = max(1, round(fps_num / (2 * fps_den)))   # 0.5 秒对应多少帧：59.94→30、29.97→15
# 音频每块样本数 = 该视频块覆盖的时间 × 48000（两种帧率都得到 24,024）
```

门禁已加两条硬检查：`视频/音频分块尺寸 == 0.5 秒`（`verify-output.py`）。
**相机自己的原片和新输出都必须通过，这是可以自证的判据。**

### 4.7 ★ PTL：tier 一律 High(1)，level 按帧率（150 / 123），且流内与 hvcC 必须相同

**两个相机原片的实测值**（都是 High tier）：

| 原片 | `general_tier_flag` | `general_level_idc` |
|---|---|---|
| `DSC_8955.MOV`（1080p60）| **1（High）** | **150（5.0）** |
| `DSC_8960.MOV`（1080p30）| **1（High）** | **123（4.1）** |

**踩的坑（两个叠加，而且门禁完全没查这两个字段）：**

1. x265 参数里写死了 `level-idc=5.0` → 29.97 输出本该是 **4.1(123)**，写成 5.0 → 相机不认；
2. **x265 的 `high-tier=1` 不保证生效** —— 实测 640×360 写出 tier=1，
   同样参数改成 1280×720 就写回 **tier=0**（它按码率/VBV 自己判断）。
   于是**流内 PTL 是 150/Main，而 `hvcC` 写的是 150/High —— 两者矛盾**。

后果：29.97 **完全播不了**；59.94 能播但**快进卡死**（相机跳转时会重读流内 PTL）。

**修法**：不依赖编码器，用 `hevc-ps.set_ptl()` **按语法定位后直接写**：

```python
lv_f, lv_idc = (5.0, 150) if 帧率 > 40 else (4.1, 123)   # 同时喂给 x265
vps_f = hevc_ps.set_ptl(vps_f, lv_idc, tier=1)           # 流内写死 High tier
sps_f = hevc_ps.set_ptl(sps_f, lv_idc, tier=1)
# hvcC 用同一个 level_idc：hvcc(..., level=level_idc)
```

`hvcC` 记录体偏移：`体+1` 的 bit5 = tier_flag，`体+12` = general_level_idc。

**门禁补了 3 条**（共 45 项）：`general_tier_flag == High(1)`、
`general_level_idc == 150/123`（按视频时基）、`hvcC 的 PTL == 流内 PTL`。
相机两个原片都能过，这是可以自证的判据。

> ⚠️ 教训：**门禁没覆盖的字段就等于没验证。** 那两个字段漏了，
> 于是"42/42 全过"的坏文件一路发到相机上。

## 6. 门禁：43 项（`verify-output.py`）+ 附加审查（`--extra`）

拷卡前必须 **43/43**。检查内容：

1. 顶层布局（`ftyp` / `moov` / `mdat` 位置）
2. 轨道结构（`stbl` 子盒与模板一致）
3. **时长自洽**：`mvhd` 覆盖最长轨道、`mvhd.timescale == 视频轨时基`、
   两条轨道的 `tkhd.duration == 轨道时长`
4. **NCDT**：存在、子盒同序、帧数 == 实际帧数、帧率推导时长 == 容器时长、
   本地时间 == 容器 UTC + 时区、**3 张缩略图的结构与解码**
5. **参数集与切片头 vs 相机 31 个字段**（★ 必须 trace 到 **P 帧**，同名取最后一次出现）
6. 整体解码 0 错误

> ⚠️ 教训：早先只查 20 个 SPS/PPS 字段、只看第 0 帧（IDR），**漏掉了 NVENC 那 16 处差异**，
> 还给自己加过"GPU 豁免"把坏文件放进门禁。**不要放宽这个门。**

**附加审查（可选，`--extra`）**：`tools/nikon-box-audit.py`，20 项（含 ffprobe 逐包对照；
`--no-ffprobe` 时 19 项）。依据是外部研究逆向出的**尼康固件自己的 ISO BMFF 解析器**所接受的子集
——恰好一个 `moov` 且 ≤16 MiB、`stco/co64` 二选一、`stsc` 首项 chunk=1/spc≠0/sdi=1/块号严格递增、
表长度精确自洽、样本落在 `mdat` 内且单调不重叠、**无 `ctts` 重排**、`mdat` 数据区无空洞
（相机同款的 8 字节全 0 首部前缀除外）。它是**独立实现**（不用 `boxio`），所以能反过来验证我们的工具；
阴性对照（截断 1 字节 / 偏移 ±4·±8·±4096 / 样本长度改 0 或 2³¹-1）全部能被它抓住。
细节与出处见 `docs/尼康ISO-BMFF子集-参考.md`。

## 7. 踩过的坑（完整清单，避免重复踩）

### 7.1 容器 / 时间

| 坑 | 现象 | 修法 |
|---|---|---|
| **分块规则搞错（以为"每 30 帧一块"）** | 相机其实是「**每 0.5 秒一块**」：29.97 时视频该 **15 帧**（用了 30）、音频该 **24,024**（算成一半或 48,048）→ **播到一半跳出 / 完全无法播放** | `VPC = 帧率/2`，音频按同一段时间折算（见 §4.6）|
| **`--jobs > 1` 分段并行（v1）** | 单进程正常（`DSC_4537`），v1 分段并行**播到 20-35 s 就跳出**（`DSC_4534`/`DSC_4535`）| **v2 已修**：段边界取 30 帧倍数（v1 段长 3816 帧不是 30 的倍数，第 2 段起 IDR 位置整体偏 6 帧）、输出式 seek 加 1/4 帧余量防 ±1 帧吞帧；工具编完自检 IDR 节奏（`check_idr_cadence`，违例直接报错）。注意"重复参数集"不是原因——打包容器本来就丢弃全部非 VCL NAL。真机复验通过前默认 `--jobs 1` |
| `tkhd.duration` 漏改 | 相机显示时长错 | 两条轨道都按影片时基写 |
| 视频时基写 `30` | 快进 2× + 时长错 + 音视频不齐 + 播不全 | 归一到 `30000/1001` |
| `mvhd.timescale` 用模板的 60000 | 与视频轨不一致 | 改成等于视频轨时基 |
| 帧数按未归一的帧率算 | 视频比音频长 0.06 s | 先 `normalize_fps` 再算 |
| `mvhd.duration` 写视频时长 | 音频尾部被切 | 取最长轨道 |
| `elst` 用轨时基 | 时长错 | 用**影片时基** |
| 改缩略图后没重建 `udta` 的 size | 整棵 moov 解析错位（连 NCDT 都找不到）| 子盒尺寸变了就重建外层 size |
| `stsz` 紧凑格式漏 4 字节 version/flags | 字段错位 | `struct.pack(">III",0,sample_size,count)` |
| `stsd` 重装时写了两遍 entry size | `invalid STSD entries` | entry 自带 size，别再加 |
| 递归替换参数集时漏了 `edts`/`dinf`/`udta` | `elst` 没被改 → 播放只到前几秒 | 递归列表补全 |
| `find()` 从容器起点开始 | 容器把自己当第一个同级盒 → 找不到子盒 | 从 `容器偏移 + 8` 开始 |
| 交错拼接用 `sum(v_per[:k])` | O(n²)，长片会卡死 | 用累计下标 |

### 7.2 码流 / 参数集

| 坑 | 现象 | 修法 |
|---|---|---|
| **`keyint` 写死 30** | 29.97 的 0.5 s 块 = **15 帧**，写死 30 → 一半块不以 IDR 开头（2026-10-07 定位的 29.97 第二根因）| `gop = max(1, round(帧率/2))`：59.94→30、29.97→15；keyint/min-keyint/gop/check_idr_cadence 同源 |
| **PTL 的 tier/level 写错，且流内与 `hvcC` 矛盾** | **相机不认（29.97 完全播不了；59.94 能播但快进卡死）** | tier 跟随相机原片：59.94→0、29.97→1；level 按帧率 150/123；**流内与 hvcC 必须相同**（见 §4.7）|
| **门禁漏查 PTL** | 上面那个矛盾文件一路 42/42 全过 → 假安全感 | 已补 3 条检查（tier / level / hvcC 一致性），共 43 项 |
| **`--jobs > 1` 分段并行（v1）** | 单进程正常，分段并行播到 20-35 s 就跳出 | **v2 已修**：段边界取 30 帧倍数 + IDR 节奏自检（见 §7.1 同名行）；真机复验通过前默认 `--jobs 1`，`--jobs 0` 自动按片长选 |
| 没编 1088 / 无 `conformance_window` | **能识别但读取无限加载**（根因）| 补 8 行 + 插裁剪窗口 |
| x265 默认开放 GOP | 关键帧是 CRA(21) → 卡加载 | `open-gop=0` |
| x265 默认 WPP | 切片头多 entry points | `wpp=0` |
| AUD 写成 `08`/`18` | P 帧被标成 I | 改成 `10`/`30` |
| `hvcC` 的 `profile_idc` 写 0 | 非法 | 写 1（Main）|
| VPS/SPS constraint flags 与 `hvcC` 自相矛盾 | 相机不认 | 流内与 `hvcC` 一起清零 |
| 色彩用 ffmpeg 的 `-color_primaries` | 写成"未指定"(2)，相机是 bt709(1) | 用 **x265 原生参数名** `colorprim=bt709:transfer=bt709:colormatrix=bt709:range=full` |
| `-sar 0:0` | libx265 报 `Value nan` | 别加；用 `sps` 里删掉 `aspect_ratio_info` |
| `tu-inter-depth=0` | x265 要求 ≥1，编码失败 | 别加，默认就是 0 |
| **VPS 时序信息"插在"而非"替换"原 flag 位** | VPS 之后的 SPS/PPS 全不被解析 | **替换**那一位 |
| VPS 漏读 `vps_reserved_0xffff_16bits` | 后续全部错位 | 补 16 位 |
| `profile_tier_level` 里 `general_level_idc` 位序放错 | 错位 | 它在 constraint flags 之后、子层 present 之前 |
| Annex-B 尾部多余 `00` 字节 | 改字段后停止位错乱 | 按"最后一个 1 位"规范化尾部 |
| PPS `lists_modification_present_flag` 单独翻 | 切片头解析错位（574 个解码错误）| **不要单独改**，它必须与切片头里的语法同时存在 |
| `num_negative_pics` 拿来当判据 | 能播的文件也不一致（2 vs 1）| 它不是相机判据，别放进必须一致清单 |

### 7.3 缩略图

| 坑 | 现象 | 修法 |
|---|---|---|
| 塞普通 JPEG 进 NCDT | **相机拒绝整个文件** | 用 `camera-jpeg.pillow_camera_jpeg()` |
| ffmpeg + 改 SOF 采样率 | JPEG 损坏（每张 2 个解码错误）| 走 Pillow（libjpeg `subsampling=1` 正好是 4:2:2）|
| `ncdt_jpegs` 偏移算错 | 取不出 JPEG | `find(b"NCDT")` 给的是**类型字段**位置，子盒从 `+4` 开始 |

### 7.4 其它

- `find` / `glob` / `grep` 用专用工具，别用 shell 顶替。
- 临时文件**按输出名区分**（`enc-<tag>.265`），并发转多个文件才会不互相踩。
- **帧数自检**：编完立刻核对"帧数 ≈ 时长 × 帧率"，差 >2% 直接报错。
  （踩过：视频被截短成 9,824 帧，视频 163.9 s 而音频 254.9 s。）
- 变量名别重用：帧数自检里的 `fn, fd` 曾把函数级的整数帧率覆盖成浮点 → `struct.error`。
- **`edit`/`write` 会吃掉 UTF-8 BOM**：改完 `.ps1` / `.cmd` 必须补回，否则 PowerShell 5.1
  按 GBK 读，中文注释直接变成语法错误：
  `[IO.File]::WriteAllText($p, [IO.File]::ReadAllText($p,[Text.Encoding]::UTF8), (New-Object Text.UTF8Encoding($true)))`
- **`app/build-exe.ps1` 里调 PyInstaller 要临时放宽 `$ErrorActionPreference`**：PyInstaller 的
  INFO 日志走 stderr，在 `Stop` 模式下会被 PowerShell 当成 `NativeCommandError` 直接终止；
  收尾的 `Format-Table` 与前面的 `Write-Host` 混用还会抛 `ConsoleLineOutputOutOfSequencePacket`。
  脚本里已改成 `Invoke-PyInstaller` 包裹 + 纯文本打印。
- **pip 装 PyInstaller 时留意代理**：本机 Clash 在 `127.0.0.1:7897`，没开时 pip 会
  `ProxyError: Cannot connect to proxy`。清掉 `HTTP_PROXY`/`HTTPS_PROXY`（含小写）后
  `pip install --isolated -i https://pypi.tuna.tsinghua.edu.cn/simple PyInstaller pillow`。

## 8. 性能（实测，可继续优化）

瓶颈 100% 在 x265 编码（97.8%）；滤镜链单独跑 1,516 fps。

**根因**：相机的两条要求恰好掐死 x265 的并行度 —— `wpp=0`（CTU 行内并行没了）
+ `bframes=0`（帧级并行没了）→ 1080p 只有 12–14 fps，**换 preset 几乎没用**。

| 措施 | 实测收益 | 状态 |
|---|---|---|
| 单进程线程调优 `pools=4` | 228 帧直编 41.1 s → 26.3 s（1.6×）| ✅ 已实现 |
| 分段并行 v2 `--jobs 4`（GOP 对齐）| 编码 226.6 → 118.9 s（**1.91×**，1824 帧实测）| ✅ 已实现 + 自检；**真机复验进行中**，通过前默认 `--jobs 1` |
| 不复制帧 `--fps source`（29.97）| 2.0× | ✅ 已实现；29.97 keyint 修正后 43/43 门禁 + 逐字节对齐全过（2026-10-07 真机通过）|
| 两者叠加（v1 时代实测）| **1248 s → 605 s（2.06×）** | v1 数字；v2 叠加预期更高 |
| `wpp=1` | 2.0× | ⚠️ 未验证：会改 PPS 字段 + 切片头多 entry points，需真机试 |
| GPU(NVENC) | ~10× | ❌ 相机不认 |

**v2 实测细节**（2026-10-06，1824 帧 = 8×DSC_8955 拼接，15 Mbps / preset fast）：
jobs=1（pools=4）编码 226.6 s（8.1 fps）vs jobs=4（每段 pools=3）118.9 s（15.3 fps）
= **1.91×**；两轮 43/43 门禁全过、61 个 IDR 全部落在 30 的倍数帧、体积差 1.7%。
机器是 6 物理/12 逻辑核：x265 重负载下 SMT 增益小，聚合吞吐天花板 ≈15 fps；
**短片（每段几十帧）并行反而更慢**——每段要摊 x265 启动+找帧开销，所以 `--jobs 0`
自动模式在片子短于约 25 s 时回落单进程（时长阈值，帧率无关）。

**29.97 基准**（2026-10-07，`DSC_9698.MOV` 全片 966 帧 / 32.2 s，15 Mbps / preset medium）：
jobs=1 总 129.2 s vs jobs=4 总 73.0 s = **1.77×**；**jobs=6 65.4 s = 1.98×（最优，
每段 2 线程）**，jobs=8 回落 66.6 s。`--jobs 0` auto 已按帧率分支：29.97 自动选 6 段
（70.4 s，43/43，产物与显式 jobs=6 同尺寸）；59.94 维持 4 段——6 段实测明显变慢
（171.1 s vs 118.9 s，每段只剩 2 线程，复杂内容欠并行）。GOP=15 后 IDR 密度与
59.94 相同（每 0.5 s 一个），medium 吞吐 ≈8 fps。

**体积由码率决定，跟帧数关系不大**：ABR 下 15 Mbps ≈ 478 MB。
要更小就降 `--bitrate`（720p 上采样源 8M 也够）。

## 11. 相机卡操作纪律（务必遵守）

1. **绝不在没有校验过副本的情况下删相机原片。** 删卡前先 `copy-to-card.py`/`clear-card.py`
   在本机留副本并核对 SHA256。
2. 卡上 `_DSC*.NEF` 是用户拍的照片，`NC_FLLST.DAT` 是相机的索引文件，**都不要动**。
3. 拷完 `copy-to-card.py` 会刷新写缓存；**拔卡前确认它打印"可以拔卡"**。
4. 文件名要避开相机已用编号（`copy-to-card.py` 会检测冲突）。
5. 相机只认它自己那套参数——**任何"看起来等价"的简化都可能被拒**，一律以真机为准。
