## 一、一条命令完成转换

```powershell
$py = 'python'
$env:PYTHONIOENCODING='utf-8'

# 模板用相机实拍的同分辨率 MOV（1080p 视频就用 DSC_8955.MOV）
& $py -B tools\video-to-camera-mov.py 你的视频.mp4 `
    --out DSC_4500.MOV `
    --template F:\DCIM\118NZ5_2\DSC_8955.MOV

# 拷到卡上（自动 SHA256 校验 + 编号冲突检测）
& $py -B tools\copy-to-card.py DSC_4500.MOV
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--bitrate 40M` | 视频码率（相机自己的 1080p 约 73 Mbps，所以 40M 很安全）。**源是 720p 上采样时 40M 属于浪费，15M 就够（4 分 15 秒的片子 982 MB → 约 400 MB）** |
| `--size 1920x1080` | 输出分辨率（不足会等比放大 + 黑边填充）|
| `--fps 60000/1001` | 输出帧率，相机 1080p60 就是 59.94 |
| `--time now` | **拍摄时间**，默认用当前时间；也可给 `'YYYY:MM:DD HH:MM:SS'`（本地时间），或 `keep` 沿用模板 |
| `--duration 30` | **只取前 30 秒**（帧数与所有时长字段会一起改对）|
| `--preset fast` | x265 预设。4 分 15 秒的片子 `fast` 约 15 分钟、`medium` 约 40 分钟；实测 `fast` 的关键 SPS 字段仍与相机一致 |
| `--start 10` | 从第 10 秒开始（配合 `--duration`）|
| `--no-thumbs` | 不重建缩略图（默认用视频首帧重建 3 张）|
| `--no-audio` | 只留静音轨 |
| `--keep` | 保留中间 `.265` / `.pcm` / `.jpg` 便于排查 |

### 拍摄时间要改两套（重要）

相机在**两个地方**存时间，且都用得上：

| 位置 | 内容 | 例子 |
|---|---|---|
| `mvhd` / `tkhd` / `mdhd` 的 creation+modification | QuickTime 纪元秒（**UTC**）| `13:55:00` |
| `NCDT` 的 `NCTG 0x11` / `0x12` | ASCII 本地时间 | `2026:10:01 21:55:00` |
| `NCTG 0x19` | 时区 | `+08:00` |

**只改一套会自相矛盾。** 本工具按 `NCTG 0x19` 的时区把本地时间换算成 UTC，两套一起写。
默认 `--time now`，否则相机里会显示模板那条片子的拍摄时间（实测就是这个问题）。

实测只改时间时，文件与"已验证能播"的版本**只差 42 个字节、全在 moov 里**，
视频样本一个字节没动。


## 二、工具做了什么

```
源视频 ─┬─ 视频：hevc_nvenc 编码（H.265 Main / 8-bit / 无 B 帧 / GOP 30 / 每样本带 AUD）
        │        参数集抽到 hvcC，样本里只留 AUD + 切片（与相机完全一致）
        ├─ 音频：抽成 PCM 24-bit 48 kHz 立体声（相机 MOV 就是这个格式）
        └─ 容器：套相机 MOV 骨架（ftyp qt+niko | moov | free | mdat@655,360）
                 两条 trak 的 tkhd/mdhd/hdlr/minf/stsd 结构照抄模板，
                 只重算 stsz/stsc/co64/stss/stts 与时长
                 NCDT 帧数字段改成实际帧数
```

**为什么能做到"相机同构"**：容器骨架整段来自相机实拍文件，不是我自己拼的。
只有样本数据和 `hvcC` 是新的。

### 验证过的硬指标

| 项目 | 结果 |
|---|---|
| 单文件往返（相机原片 → 重封装）| **SHA256 完全相同**（MP4 与 MOV 都通过）|
| 每样本 NAL 结构 | AUD + 切片，2 个/样本，与相机一致 |
| AUD 字节 | `46 01 08`（IDR）/ `46 01 18`（P）|
| 切片类型 | 全 I/P，**无 B 帧** |
| IDR 间隔 | 30 帧 |
| 音频 | PCM 24-bit 48 kHz 立体声，`sample_size=6` |
| 顶层布局 | `ftyp(24) moov free mdat@655,360`，与 `DSC_8955.MOV` 逐项对应 |

## 三、相机实测结论：**已打通** ✅

| 文件 | 内容 | 相机结果 |
|---|---|---|
| `DSC_4450.MOV` | 相机 1080p 原片逐字节复制、只改文件名 | ✅ 能播（外部文件被接受）|
| `DSC_4470.MOV` | 相机码流 + 本工具重建的容器 | ✅ 能播（容器重建正确）|
| `DSC_4483.MOV` | 补齐参数集 + **编 1088 + conformance_window** | ✅ **能播** |
| `DSC_4484.MOV` | 全部补齐 | ✅ **能播** |

### 根因：相机编的是 1088，不是 1080 ★

| 字段 | 相机 `DSC_8955.MOV` | 本工具（原来）|
|---|---|---|
| `pic_height_in_luma_samples` | **1088** | **1080** |
| `conformance_window_flag` | **1** | 0 |
| `conf_win_bottom_offset` | **4**（裁 4×2 = 8 行）| — |

1080 不是 16 的倍数，硬件编码器习惯**编 1088、再用 `conformance_window` 裁掉 8 行**。
本工具原先按 1080 直接编、没有裁剪窗口，相机就"能识别但读取无限加载"。

**修法**（已固化）：编码高度取"显示高度向上取到 16 的倍数"，1080 → 1088，
`conf_win_bottom_offset = (1088-1080)/2 = 4`，正好就是相机的取值。

### 这一路上排掉的其它差异

| # | 差异 | 相机 | 原来 | 现象 |
|---|---|---|---|---|
| 1 | **conformance_window / 1088** | 有 | 无 | 能识别但读取无限加载 |
| 2 | 关键帧类型 | 全 IDR_W_RADL | **19 个 CRA** | 卡在加载（x265 默认开放 GOP）|
| 3 | WPP / entry points | 0 / 无 | 1 / **16 个** | 解码器不认 entry point |
| 4 | AUD `pic_type` | `10`/`30` | `08`/`18` | P 帧被标成 I 帧 |
| 5 | CTU / 最小编码块 / TU 深度 | 64 / 8×8 / 0 | 32 / 16×16 / 3 | NVENC 给不出 CTU 64 → 换 x265 |
| 6 | `hvcC` 的 `profile_idc` | 1 (Main) | **0（非法）** | 记录头非法 |
| 7 | VPS 时序信息 | 有（1001/60000）| 无 | 帧率时序缺失 |
| 8 | DPB / latency | 1 / 0 | 2 / 1 | 缓冲声明不一致 |
| 9 | `sign_data_hiding` / `weighted_pred` | 0 / 0 | 1 / 1 | 编码工具不一致 |
| 10 | 色彩 / full range / aspect_ratio | bt709 / 全范围 / 无 | 未指定 / 有限 / SAR | VUI 声明不一致 |
| 11 | VPS/SPS 的 constraint flags | 0 | `F0`（还与 `hvcC` 自相矛盾）| — |

### 仍存在的 4 项差异（不影响播放，实测）

- `lists_modification_present_flag`（**不能单独补**：翻这一位会让切片头解析错位）
- `sps_scaling_list_data_present_flag`（x265 只有 `default`/`off`，拿不到显式列表）
- `num_short_term_ref_pic_sets` / `short_term_ref_pic_set_sps_flag`
  （相机把参考图像集放 SPS，本工具切片头内联）

**结论：这 4 项不影响相机播放。**


## 三之二、NCDT 里的缩略图与"时长"

### NCDT 的子盒结构（实测）

| 子盒 | 内容 | 1080p 文件 | 4K 文件 |
|---|---|---|---|
| `NCHD` | 18 B 固定头（`Nikon`+版本），**三个文件完全相同** | 18 B | 18 B |
| `NCTG` | 元数据记录 | 5,561 B | 5,561 B |
| `NCTH` | **JPEG 160×120**（列表小图）| 4–6 KB | 4 KB |
| `NCVW` | **JPEG 全分辨率**（大预览）| ~484 KB | ~1.49 MB |
| `NCM1` | **JPEG 640×360**（中图）| ~43 KB | ~28 KB |
| `NCM2` | **JPEG 1920×1080** | 8 B（空盒）| ~334 KB |
| `NCDB` | 8 B 空盒 | 8 B | 8 B |

模板那几张 JPEG 是**模板那条片子**的画面——不换，相机会把别人的画面当缩略图。
本工具现在用**视频首帧**重建 `NCTH` / `NCM1` / `NCVW`（尺寸取自相机实测），
`--no-thumbs` 可关闭。

### ★ 缩略图必须写成"相机风格"的 JPEG，否则相机拒绝**整个文件**

实测相机与 ffmpeg 默认输出的差别（**只是塞进普通 JPEG，相机就报"无法显示"**）：

| 项 | 相机 | ffmpeg 默认 |
|---|---|---|
| Y 采样 | **2:1（4:2:2）** | 2:2（4:2:0）|
| 量化表 | **2 张**（亮/色各一，DQT 段长 132）| 1 张（段长 67）|
| 标记序列 | `DQT DHT SOF0 SOS` | `APP0(JFIF) COM DQT DHT SOF0 SOS` |

**踩过的坑（重要）**：一开始用 ffmpeg 的 `-pix_fmt yuvj422p` 编码，然后把 SOF 里的采样率
改成相机的 `2:1/1:1/1:1`。**这是错的**——ffmpeg 的 mjpeg 即使给 yuvj422p，写出来的
采样率其实是 `2:2/1:2/1:2`；只改 SOF 的声明、不改熵编码数据，JPEG 直接损坏
（实测每张 2 个解码错误，`error y=0 x=0`），相机于是拒绝整个文件。

**正确做法（`tools/camera-jpeg.py` 的 `pillow_camera_jpeg`）**：走 Pillow(libjpeg)

1. 用**相机那张量化表** + `subsampling=1` 编码 —— libjpeg 的 4:2:2 正好是 `2:1/1:1/1:1`；
2. DHT 与相机**逐字节相同**（都是标准 Annex K 表），无需改；
3. 把 DQT 合成一段（两张表）、DHT 合成一段、**重排成相机的顺序** `DQT DHT SOF0 SOS`；
4. 去掉 `APP0`(JFIF) 与 `COM` 注释段。

**校验口径**：产出缩略图的标记序列、采样率、量化表段数都与相机一致，
且 `ffmpeg -v error` 解码 **0 错误**（改 SOF 那一版是每张 2 个错误）。

### 时长：NCDT 里**没有**时长字段

对比三段时长不同的相机原片（228 帧 / 3.80 s、384 帧 / 6.41 s、144 帧 / 2.40 s）：

- `NCHD` 三个文件**完全相同**，`NCDB` 是空盒；
- `NCTG` 的记录里**没有任何时长字段**，与内容相关的只有：
  - `0x13` = `[帧数, 0]`（228 / 384 / 144）★
  - `0x16` / `0x17` = 帧率 `60000/1001`
  - `0x11` / `0x12` / `0x1002` = 拍摄时间
  - EXIF 类：`0x110829d` 光圈、`0x1108832` ISO

**所以相机的时长 = `NCDT` 帧数(`0x13`) ÷ 帧率(`0x16`)。**
本工具把 `0x13` 改成实际帧数，并让容器 `mvhd` 时长、`mdhd`/`elst` 同步，三者自洽
（例：300 帧 → 5.0050 s，容器也是 5.0050 s）。

**`--duration N`** 只取前 N 秒（`--start S` 指定起点），帧数与所有时长字段会一起改对。

### 坑：改缩略图会改变 NCDT 大小，外层 `udta` 的 size 必须重建

帧数 / 时间是**等长改写**，不会暴露这一点；换缩略图会变长变短。
只换 `NCDT` 的字节、不重建 `udta` 自己的 size 字段，整棵 moov 会解析错位
（现象：连 `NCDT` 都找不到）。


## 四、性能优化（实测数据）

### 瓶颈在哪

以 4 分 15 秒的片子（`DSC_4521`，15,267 帧）为例：

| 阶段 | 时间 | 占比 |
|---|---|---|
| **视频编码（x265）** | **1220.0 s** | **97.8 %** |
| 打包容器 | 26.7 s | 2.1 % |
| 缩略图 | 0.6 s | |
| 音频 | 0.5 s | |
| 探测 | 0.1 s | |
| **合计** | **1247.9 s** | |

**滤镜链单独跑是 1,516 fps**（0.8 s / 1200 帧）——完全不是瓶颈。

### 为什么 x265 这么慢

**相机要求的两项恰好掐死了 x265 的并行度**：

- `wpp=0` → `entropy_coding_sync_enabled_flag=0`（相机是 0）→ **CTU 行内并行没了**
- `bframes=0` → 相机无 B 帧 → **帧级并行几乎没了**

结果 1080p 只有 **12–14 fps**，而且**换 preset 几乎没用**（实测 20 秒片段：
medium 21.7 fps、ultrafast 19.1 fps——ultrafast 反而更慢）。

对照实验（20 秒，1200 帧，ultrafast）：

| 配置 | 时间 | fps |
|---|---|---|
| `wpp=0, bframes=0`（当前）| 87.4 s | 13.7 |
| `wpp=1, bframes=0` | **43.9 s** | **27.3（2.0×）** |
| `wpp=1, bframes=3` | 40.6 s | 29.6（2.2×）|
| `wpp=0, bframes=3` | 78.6 s | 15.3 |

### 可用的优化（按收益排序）

| # | 措施 | 实测收益 | 状态 |
|---|---|---|---|
| 1 | **分段并行** `--jobs 4` | 编码 **2.14×**；端到端 1.6× | ✅ 已实现，33/33 过门禁 |
| 2 | **不复制帧** `--fps source` | 帧数减半 → **2.0×** | ✅ 已实现，33/33 过门禁；**相机认不认 29.97 待真机验证** |
| 3 | `wpp=1` | **2.0×** | ⚠️ 需相机验证（改 PPS 字段 + 切片头多 entry points）|
| 4 | GPU（NVENC）| ~10× | ❌ 相机不认（见上文）|

**1+2 叠加实测**（同一段 4 分 15 秒）：

| 配置 | 编码时间 | 总时间 | 文件 |
|---|---|---|---|
| 原配置（59.94 fps、单进程）| 1220 s | 1248 s | 982 MB |
| **`--jobs 4 --fps source`** | **590 s** | **605 s** | 547 MB |

**→ 2.06×（20.8 分钟 → 10.1 分钟）**，33/33 过门禁，文件 `DSC_4532.MOV`。

### 关于体积

ABR 下体积由**码率目标**决定，跟帧数关系不大：
15 Mbps × 254.7 s ≈ 478 MB，实测 380–547 MB 波动。
**要更小就降 `--bitrate`**（源是 720p 上采样时 8M 也够）。

## 四之二、时基必须用相机的约定 ★（踩过两个大坑）

### 坑 ①：`tkhd.duration` 一直没改

模板里它是模板那条片子的值，**每一条轨道都要按影片时基写成本轨道的时长**。
漏改的后果：相机里显示的时长是错的。

### 坑 ②：视频时基不能写成 `30`，要写 `30000`

拿**用户实拍的 30fps 原片** `DSC_8960.MOV` 做对照，相机的"标准答案"是：

```
mvhd.timescale       = 30000      （= 视频轨时基）
视频 mdhd.timescale  = 30000      stts delta = 1001   -> 1001/30000 = 29.97 fps
NCDT 0x16/0x17       = 30000/1001
tkhd.duration        = 195195     （= 6.5065 s）
```

而我一开始把 30fps 写成 `30/1`（视频时基 = **30**）。数学上等价，但
**相机只认它自己那套时基（60000 / 30000）**，看到 `30` 就退回默认的 1080p60 模式，
于是四个症状同时出现：

> **2 倍快进 + 时长显示错 + 音视频不齐 + 视频播不全**

59.94 那版本本来就用 `60000/1001`（时基 60000），正好撞对，所以这个坑一直没暴露。

**修法**：`normalize_fps()` 把输出帧率归一到相机的约定
（23.976→24000/1001、**29.97/30→30000/1001**、59.94/60→60000/1001…），
并且：
- `mvhd.timescale` = 视频轨时基
- **帧数按归一后的帧率算**（`30/1` 要先变成 `30000/1001` 再算，否则 60 秒会变 60.06 秒）
- `tkhd.duration` / `elst` 都按影片时基写

### 对照表（修正后）

| 字段 | 相机 30fps 原片 | `DSC_4535`（本工具）|
|---|---|---|
| `mvhd.timescale` | 30000 | **30000** ✓ |
| 视频 `mdhd.timescale` | 30000 | **30000** ✓ |
| `stts` delta | 1001 | **1001** ✓ |
| 视频 `tkhd.duration` | 195195 | **7642635**（=254.7545 s）✓ |
| 音频 `tkhd.duration` | 195195 | **7642648**（=254.7549 s）✓ |
| `NCDT 0x16/0x17` | 30000/1001 | **30000/1001** ✓ |
| 音视频时长差 | 0 | **0.0004 s** ✓ |

门禁相应加了 3 项：`mvhd.timescale == 视频轨时基`、两条轨道的
`tkhd.duration == 轨道时长`。现在共 **40 项**。

## 五、链路现状（已打通）

```
普通电脑视频（任意分辨率/帧率/编码）
        ↓  tools/video-to-camera-mov.py
相机可播 MOV（1080p59.94 H.265 + PCM24，含自洽 NCDT + 自建缩略图 + 正确时间）
        ↓  tools/verify-output.py          ← 一键门禁，40 项全过才拷
        ↓  tools/copy-to-card.py
卡上 → 相机播放                                 ✅ 真机验证通过
```

**门禁口径（40 项）**：顶层布局、轨道结构、**时长自洽**、`NCDT` 帧数/时间/**缩略图
（含解码验证）**、**参数集与切片头 33 个字段**、整体解码。

> ★ 参数集检查必须 **trace 到 P 帧**（同名取最后一次出现），并且覆盖
> **PPS 级开关**（`cabac_init_present_flag` / `deblocking_filter_control_present_flag` /
> `num_ref_idx_active_override_flag`）和 `nal_hrd_parameters_present_flag`。
> 只查 20 个 SPS/PPS 字段 + 只看第 0 帧（IDR）**会漏掉 GPU 版那 16 处差异**
> —— 我就是这么让 `DSC_4511` 通过了门禁、结果相机不认。

## 五、已知的不确定点

- **`hvcC` 的 VUI 细节**：本工具的 hvcC 比相机的小（相机 SPS 里带 372 字节显式
  scaling list），实测**不影响播放**。
- **更长的片子**：目前真机验证最长 10 秒。长片未测，但容器重建已由
  `DSC_4470.MOV`（10.2 秒、相机原生码流）验证正确。
- **4K**：模板用 4K 的 `DSC_8951.MOV` 时缩略图会大很多（`NCM2` 要用 1920×1080），
  本工具目前只重建 `NCTH`/`NCM1`/`NCVW`，`NCM2` 保持模板原样。
